### Provider mapping evidence and revision history

The previous mapping path persisted the active SKU and latest reviewer and approval time. Its optional identity preview did not durably preserve the source, pack and GTIN evidence, competing decisions, or earlier mappings. V11 adds `provider_mapping_decisions` for these records. It creates an empty table and does not backfill approvals or update existing listings or observations.

| Admin route | Behavior |
|---|---|
| `POST /api/admin/provider/mapping/review` | Read-only review of the submitted identity and the canonical product, pack and barcode. The result is advisory. |
| `POST /api/admin/provider/mapping/decisions` | Append a `REJECTED` or `UNRESOLVED` decision. This does not activate the proposed SKU or revoke an active mapping. |
| `PUT /api/admin/provider/mapping` | Explicit approval using `variantId`, `platform`, `retailerSku`, `listingIdentity`, and `mappingEvidence`. A legacy request without evidence can only replay an already approved active SKU. Known pack and barcode conflicts, unconfirmed pack compatibility, and unresolved identity fields block a new approval. Existing current and historical observations block SKU reassignment. A failed approval does not append a review. The reviewer uses the decision route to record the disposition. |
| `GET /api/admin/provider/mapping/decisions` | Read revisions in ascending order by `variantId` and `platform`, with up to 100 entries after the optional exclusive `afterRevision` cursor. |

`mappingEvidence` contains `decisionId` (UUID), `sourceProvider`, `sourceRecordId`, `evidenceReference`, `evidenceSha256` (lowercase hex), `permissionReference`, `rationale`, and optional `supersedesDecisionId`. Use a reference to the exact authorized evidence manifest or artifact. Keep file bytes, credentials and permission documents in the restricted workspace. Record only metadata explicitly permitted for durable retention. Each revision retains submitted identity fields, the canonical title, brand, variant, pack and registered GTINs used for review, blockers, the JWT reviewer, a server timestamp, and any prior active SKU and approval actor/time. A replay with the same decision ID and payload preserves the original row. A new decision uses a new ID and links to the latest decision for that candidate, if one exists. A new approval cannot reuse a digest from any prior rejected or unresolved decision for that candidate. Changing a rationale alone cannot satisfy that requirement.

The decision table records service-managed revisions from V11 onwards. Decisions made before V11 have no reconstructed evidence or reviewer history. The first new decision records any active legacy approval metadata present at that point. The API records the admin's evidence and permission references. It does not verify provider grants, fetch artifacts, validate referenced bytes, enforce retention expiry, or record two independent human signatures. The catalogue has no dedicated canonical formulation field for this approval check. A supplied formulation stays unconfirmed and blocks an approval. Keep the source values and record an unresolved decision rather than omitting a field to get approval. Independent human decisions, disagreements, adjudication and reproducible snapshots belong in the separate benchmark workflow. The new routes require V11. The existing `mysql-local` default remains at V7 and shared deployment needs a separately approved migration. [Human annotation protocol](PRODUCT_MATCHING_BENCHMARK.md)

## CartIQ observation and mapping boundary

The existing adapters route retailer-native SKU and six-digit PIN, enforce scope and HTTPS source-host checks, preserve tri-state stock, and do not invent missing money or timestamps. The provider observations populate the current location row and append a priced history entry when appropriate. The original observation time determines freshness. A daily file can support a historical pilot if its licence allows it. Real-time comparison requires an actual observation inside CartIQ's 15-minute freshness window.

The manually reviewed mapping is a link between the retailer-native SKU and a canonical variant. In the baseline schema, `provider_mappings` keeps the latest actor and time. It does not preserve full mapping-change history or native GTIN, packaging or source evidence per approval. The reassign guard checks both current observations and price history, and sync locks and rechecks the current SKU before persisting. The legacy observation identity gate uses brand, title containment and base pack size. Keep advisory matches and low-evidence listings in manual review. The existing V7 comparison-evidence route separately checks exact SKU, canonical name, brand, named variant, pack, current observation time, source and reviewer. The current schema has listing-level source URL and provider/time on observation rows. It lacks stable upstream observation IDs, finer-than-second event identity, immutable per-observation evidence and a full availability history. One PIN can also represent multiple stores, and CartIQ currently allows one listing per retailer and canonical variant. Preserve source events and evidence in a contract-approved store before considering a reviewed schema extension. Cap, budget and page any future sync explicitly. The existing admin sync processes at most 100 mappings per call, sequentially, with no cursor for larger catalogues. A production ingest also needs explicit retry and redelivery handling within the provider's quota and credit contract.
