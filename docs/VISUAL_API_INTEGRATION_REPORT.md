# CartIQ visual and API integration

2026-11-16 IST

## Environment

| Component | Environment |
| --- | --- |
| Website | Expo Web on [127.0.0.1:18081](http://127.0.0.1:18081), configured to use the HTTP API on a separate loopback origin. |
| Backend | Spring Boot 3.5.16, CartIQ API 0.2.0, Java 17.0.12, `local` profile on [127.0.0.1:18080](http://127.0.0.1:18080). The existing Phase 8 release JAR was used. |
| Database | A new file-backed H2 2.3.232 database, `./.runtime/visual` in the isolated evidence directory, using the repository's local MySQL compatibility mode. Flyway applied V1–V18. The built-in starter catalogue was imported and sample mode was off. |
| Browser | Installed Google Chrome 157.0.8103.79, with full-page controls exercised at 1440 × 900, 1366 × 768, and 390 × 844 CSS pixels. The mobile size is Chrome's responsive viewport. |
| Accounts | Dedicated customer, peer and administrator accounts in the isolated database. All credentials and session material are omitted. |
| External services | Retailer dispatch, recipe generation, forecasting, Firebase and external geocoding were disabled. The browser allowed requests only to the two loopback origins. A second isolated Spring Boot and H2 instance on port 18082 was used for an explicitly synthetic pricing control. |

## Network and database evidence

- **Direct HTTP** recorded 46 checks, all with the expected status and assertions. Observed end-to-end latency was 10–1,894 ms. The record includes method, complete local URL, response status, time, request ID and redacted JSON shape. [Direct requests](evidence/visual-api-integration/direct-api.json)
- **Chrome** passed 19 visual workflows at each viewport, then passed three targeted admin retests after the key fix. The main run recorded 282 Spring responses in 9–1,620 ms and the targeted run recorded 48 in 13–2,160 ms. The complete evidence set matched all **387 distinct request IDs** to Spring Boot log entries, including the separate synthetic and cart persistence controls. [Browser requests](evidence/visual-api-integration/browser-acceptance.json) · [Admin retest](evidence/visual-api-integration/browser-admin-recheck.json) · [Spring correlation](evidence/visual-api-integration/spring-request-correlation.csv)
- **H2 readback** confirmed V18, 27 catalogue packs and BCrypt prefixes for all 23 disposable accounts. The latest browser account for each viewport and the latest direct API account each had one 150 g pantry row, one revision-1 weekly plan and zero cart lines after deletion. The independent cart control had one line at its updated quantity of four. The peer had zero cart, pantry and plan rows. SQL found zero duplicate cart lines, pantry records or weekly plans, zero approved and legacy price rows in the primary environment, and zero mapping decisions. [Read-only SQL](evidence/visual-api-integration/persistence.sql) · [Database output](evidence/visual-api-integration/database-readback.txt)
- **Regression checks** passed TypeScript and all 57 frontend tests. In `ai-service`, `.\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider test_recipe_generation.py` passed 10 tests with one existing Starlette TestClient deprecation warning. The successful draft in that test used the mocked model transport.

## Defects and remaining gaps

- The cart displayed ₹0 for stores with no price and described Zepto as a future integration. It now shows “No priced items” for an empty retailer quote set, keeps unknown totals unknown, and labels partially priced totals. The click-through and persisted cart quantity were retested at every viewport. [Before](evidence/visual-api-integration/cart-before-fix.png) · [After](evidence/visual-api-integration/screenshots/1440x900-08-cart-reloaded.png)
- Admin panels reused the same React key for three sibling components. The fix gives the panels distinct account-scoped identities. The duplicate-key console errors were absent in all three targeted retests, including coverage and mapping preview. [Reproduction notes](evidence/visual-api-integration/visual-defect-before.txt) · [Retest](evidence/visual-api-integration/browser-admin-recheck.json)
- The initial launch, before the backend was ready, displayed the catalogue connection-error state. The ready backend served the same browser successfully after seeding. Chrome's main run recorded four 401 responses for signed-out refresh, six 403 responses for the disabled retailer feature, and three 503 responses for disabled AI generation. Five requests were canceled while navigating or reloading. No uncaught page errors occurred. The console still reports pre-existing circular imports and a React Native Web text-node diagnostic during startup.
- The pre-existing Chrome tab had DevTools set to **Offline**. Its Network panel showed a failed search and `ERR_INTERNET_DISCONNECTED`. A clean tab loaded the local app and rendered the Amul Taaza 1-litre result. Spring logged that handoff search as HTTP 200 in 88 ms under request ID `cd170f83-ac72-40d9-b745-88b2a6108632`. The main browser response evidence came from Chrome's Network instrumentation in fresh test contexts.
- No document-level horizontal overflow or completed broken image elements appeared in the 60 gallery captures. Horizontal product and tab carousels scroll within their own containers. External product image requests were blocked in this session and the rendered fallback art was visible. Remote image availability remains untested.
- Genuine eligible retailer prices, stock, delivery fees and historical data were unavailable. Native apps, production MySQL, a live AI draft, and eligible retailer totals remain outside this verification.

## Reproduction and safety

The frontend used `EXPO_NO_DOTENV=1`, `EXPO_OFFLINE=1` and `EXPO_PUBLIC_API_URL=http://127.0.0.1:18080/api` with `npm.cmd run web -- --host localhost --port 18081 --clear`. The JVM used the existing release JAR with `SPRING_PROFILES_ACTIVE=local`, the isolated H2 file URL, `--smartcart.sample-data=false`, `--smartcart.import-starter-catalogue=true` and a loopback CORS origin. External feature flags were disabled. The startup began with reference categories and no catalogue locations. Enabling the documented starter import supplied the Bengaluru test area and catalogue on the disposable instance.

The runner used real HTTP and an installed Chrome window. Chromium DevTools Protocol and Playwright responses supplied the request evidence. Only URLs, methods, status codes, timings, sanitized shape summaries and CartIQ request IDs were retained. Evidence excludes input passwords, authorization values, cookies, tokens, raw provider responses and browser session files.

No retailer or model calls, purchases, credits, mapping approvals or shared MySQL access occurred. The persistent QuickCommerce ledger digest stayed unchanged.
