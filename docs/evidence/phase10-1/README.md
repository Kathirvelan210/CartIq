# Phase 10.1 physical Android GPS verification

On 18 November 2026 a physical Android 16 handset (API 36, arm64-v8a) ran CartIQ in Expo Go 54.0.8 over USB. Spring Boot accepted four user-confirmed device fixes for the dedicated signed-in account. The final fix appeared on the phone at 20:30:32 IST. Its timestamp in the authenticated request was 15:00:32.654 UTC. CartIQ displayed 25 m and sent the unrounded accuracy of 25.381000518798828 m. The server received the confirmation about 26 seconds after capture. [Final capture](device-to-backend.png) · [Redacted receipt](confirmed-fix.json)

## Environment and procedure

1. Check the authorized handset with `adb get-state` and Android version with `adb shell getprop ro.build.version.sdk`. The operator unlocked the phone. Install the existing local Expo Go 54.0.8 APK with `adb install` if required. No emulator or Chrome session participated.
2. Start the existing Spring Boot JAR with `java -Xmx420m -Duser.home=. -jar <local-release-jar>` in a disposable directory. The harness supplied a random session secret, `SPRING_PROFILES_ACTIVE=local`, `SERVER_ADDRESS=127.0.0.1`, `SERVER_PORT=18101`, and `SPRING_DATASOURCE_URL=jdbc:h2:mem:gps101;MODE=MySQL;DATABASE_TO_LOWER=TRUE;DB_CLOSE_DELAY=-1`. Existing Flyway migrations reached V20. Provider credentials were excluded from the launch environment.
3. Run Metro from the repository with `node node_modules/expo/bin/cli start --go --localhost --max-workers 2 --port 18102`. The launch environment supplied `EXPO_PUBLIC_API_URL=http://127.0.0.1:18103/api`, `EXPO_NO_DOTENV=1`, `EXPO_NO_TELEMETRY=1` and `EXPO_OFFLINE=1`. Register and sign in with a disposable account on the local backend.
4. Connect Metro with `adb reverse tcp:18102 tcp:18102` and the redacting HTTP relay with `adb reverse tcp:18103 tcp:18103`. Open CartIQ with `adb shell am start -a android.intent.action.VIEW -d exp://127.0.0.1:18102 -p host.exp.exponent`. The relay forwards to port 18101. It checks the authenticated subject against the test account and records field validity, source, accuracy, timestamp recency and HTTP status. The final timestamp comparison used a second loopback relay on port 18105 forwarding to 18103. No coordinate, token, contact, device serial or authorization header appears in these records.
5. Open **Choose shopping location → Use current location**. Deny the Android permission. Read the recovery message and request again. Grant **While using the app**. Review the device accuracy and capture time before pressing **Save and use this location**. Examine the HTTP receipt for that confirmation. [Permission prompt](android-permission.png) · [Denial](permission-denied.png)
6. In Android's location permission settings for Expo Go, turn **Use precise location** off. Verify Android grants coarse permission and denies fine permission. Tap the location button and confirm the approximate fix. One acquisition timed out during investigation. With the corrected app the next explicit capture returned 2,000 m with approximate permission. [Timeout](approximate-timeout.png) · [Approximate fix](approximate-preview.png)
7. Exercise denial with further Android prompts blocked. Tap **Open app location settings** in CartIQ, restore foreground permission and enable precise location. Return to CartIQ, take a new fix, review it and save. [Settings recovery](settings-recovery.png) · [Precise fix](precise-preview.png)
8. Background the app with `adb shell input keyevent KEYCODE_HOME` and reopen it. Separately cold-start with `adb shell am force-stop host.exp.exponent` followed by the Expo URL above. Before expiry the selected location and reported accuracy were restored. Neither action submitted another position. The phone retained account-scoped selections in the existing SecureStore flow. Spring kept its confirmed positions in owner-scoped memory with the existing 15-minute validity window. [Cold restart](final-after-restart.png)
9. Compare the four confirmed requests in [backend-redacted.json](backend-redacted.json) with the [device summary](android-device-gps.json). PNGs are cropped from the handset screen to include only approved labels. The screenshots exclude system notifications, identifiers and precise coordinates.

## Scope

Android supplied fused device locations. The test did not inspect which radio or satellite contributed to a fix. PIN remains a separate approximate source and its matching paths were tested offline. The isolated app reported that external geocoding was unavailable. No lookup was issued. Standalone signed builds, additional phones and an extended on-device wait through the 15-minute expiry remain outside this evidence. [Checks and results](TEST_RESULTS.md)
